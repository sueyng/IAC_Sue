# Release Notes: Lambda S3 Reverse Proxy Infrastructure

## Version Comparison: v1 vs v2 vs v3

### v3 Update — Multi-bucket mode restored (in-place revision)

- **NEW: `APIGatewayToS3BucketMapping` parameter** — restores v1's multi-bucket routing pattern. One Lambda fronts many S3 buckets, picked by API Gateway ID.
- **Mode is inferred** from which bucket parameter is non-empty (no explicit toggle parameter):
  - `FrontendSPABucketName` non-empty → single-bucket. Lambda env var `S3_BUCKET_NAME`. Narrow IAM (`${FrontendSPABucketName}/*` + `${LambdaS3bucket}/*`). Managed `S3BucketPolicy` resource attached to the bucket.
  - `APIGatewayToS3BucketMapping` non-empty → multi-bucket. Lambda env var `API_TO_S3_BUCKET_MAP`. Wildcard IAM (`${AppShortName}-*/*` + `${LambdaS3bucket}/*`). No managed bucket policy — project team owns each routed bucket's policy.
- **Both empty is allowed** — template still deploys with NO Lambda `Environment` variables block at all (uses `AWS::NoValue`). Lambda will fail at runtime when invoked. No template-time validation.
- **Backward compatible** — existing v3 deployments do nothing; `FrontendSPABucketName` filled = same behavior as before. `FrontendSPABucketName` default changed from required → `""`. `APIGatewayToS3BucketMapping` defaults to `""`.
- **IAM scope (multi-bucket usage):** wildcard `${AppShortName}-*/*` is scoped by AppShortName only — safe because project accounts are isolated per environment (one AWS account per env), so no cross-env bucket exposure within an account.
- **Lambda code requirement:** the Lambda zip (`CodeZipFileName`) must read the env var matching the bucket parameter you filled — `S3_BUCKET_NAME` for single, `API_TO_S3_BUCKET_MAP` (with API-Gateway-ID dispatch) for multi.

**v1 → v3 migration impact:** project teams who chose the multi-bucket pattern in v1 can keep it in v3 by filling `APIGatewayToS3BucketMapping` (and leaving `FrontendSPABucketName` empty) — no Lambda code rewrite required, while still gaining the v3 VPC attach + X-Ray fix.

### v3 Updates (TISO VPC Compliance + X-Ray IAM Fix)

- **NEW: Lambda VPC attachment** — `VpcConfig` block on `LambdaS3ReverseProxy` referencing private subnets and the new dedicated SG
- **NEW: Dedicated `LambdaSecurityGroup`** — least-privilege egress only (no ingress — Lambda invoked via service plane):
  - `tcp 443 → VpcCidr1` (mandatory) for CloudWatch Logs + X-Ray Interface Endpoints
  - `tcp 443 → VpcCidr2-5` (conditional via `!If`) for shared-services / multi-CIDR / peered VPC
  - `tcp 443 → S3PrefixListId` (conditional via `!If`) for S3 Gateway endpoint reads
- **FIX: X-Ray IAM permissions** — added `LambdaS3ReverseProxyXRayWriteAccess` inline policy on `LambdaExecutionRole` (`xray:PutTraceSegments`, `xray:PutTelemetryRecords`). v2 had `TracingConfig.Mode: Active` but no IAM permission — traces silently dropped. v3 makes tracing actually functional.
- **NEW: Mandatory parameters** — `VpcId`, `SubnetIds`, `VpcCidr1`
- **NEW: Optional parameters** — `VpcCidr2-5`, `S3PrefixListId`
- **Cleanup** — the orphan `s3ReverseProxy-VPCAccess` IAM inline policy from v2 (had `ec2:CreateNetworkInterface` etc. but no `VpcConfig` consumed it) is now actually used
- `IaCVersion` tag updated `InfraPlatform-lambda-s3reverseproxy-v2` → `InfraPlatform-lambda-s3reverseproxy-v3` on all tagged resources

**Pre-deployment requirements:**
- VPC must have Interface VPC Endpoints `com.amazonaws.{region}.logs` AND `com.amazonaws.{region}.xray`, both reachable from the Lambda's `SubnetIds` (silent failure if missed — Lambda runs but logs/traces dropped)
- **S3 reachability path REQUIRED** (one of): S3 Gateway endpoint (set `S3PrefixListId` — recommended), S3 Interface endpoint reachable from `VpcCidr1-5`, or NAT Gateway. **Visible outage if missed — reverse proxy returns 504 errors immediately after upgrade.**

**⚠️ CRITICAL — UPGRADE IS NOT A DROP-IN:** v2 ran the Lambda **outside any VPC** with direct internet access. v3 attaches the Lambda to a VPC, which removes that direct internet access. If S3 reachability is not pre-configured, the reverse proxy breaks immediately and clients see 504 errors. **MANDATORY — deploy to non-prod first**, smoke test end-to-end, only then promote to prod. See `v3/README.md` "Recommended upgrade procedure" for the 3-phase procedure (pre-deployment validation → non-prod smoke test → prod with rollback plan).

**Breaking change for v2 upgraders:** project teams must add 3 new mandatory parameters (`VpcId`, `SubnetIds`, `VpcCidr1`) to their parameter file before `update-stack`. All other v3 changes are pure in-place modifies, no Lambda recreation (same `FunctionName`, same ARN preserved). The Lambda SG name is auto-generated by the template (`${AppShortName}-${EnvName}-s3ReverseProxy-sg`).

### v2 Updates

- `TracingConfig.Mode: Active` on Lambda function (latent — non-functional in v2 because IAM role lacked X-Ray permissions; fixed in v3)
- `LambdaExecutionRole` with inline policies for CloudWatch Logs, S3 access, and orphan VPC ENI policy (orphan because no `VpcConfig` was attached)
- `S3BucketPolicy` on `FrontendSPABucketName` — Allow Lambda role + Deny non-TLS-1.2 / non-SSL
- `APIGatewayInvokeLambdaPolicy` to allow API Gateway invocation
- `ParameterLambdaArn` SSM parameter for cross-stack reference
- Production environment protection — `DeletionPolicy: Retain` on stateful resources for `prod*` environments
- Standardized resource tagging — `IaCVersion: InfraPlatform-lambda-s3reverseproxy-v2`

### v1 Baseline

- Initial S3 Reverse Proxy Lambda template
- Basic IAM role with CloudWatch Logs + S3 GetObject permissions
- API Gateway invocation permission

## Migration Path

### v1 → v2 Migration

⚠️ **Not backward compatible** — v2 was a redesign, not an evolution.

Breaking changes from v1:
- **Multi-bucket routing dropped** — `APIGatewayToS3BucketMapping` parameter removed; replaced by single-bucket `FrontendSPABucketName`
- **Lambda env var renamed** — `API_TO_S3_BUCKET_MAP` → `S3_BUCKET_NAME`. **Lambda code must be rewritten** (multi-bucket dispatch logic replaced by single-bucket fetch)
- **VPC attachment removed** — `VpcConfig`, `LambdaSecurityGroup`, and `SecurityGroupIngressAZ1/2/3` resources all dropped. Lambda runs with direct internet egress.
- **Parameters dropped**: `VpcId`, `SubnetIds`, `VPCSubnetCidrAZ1/2/3`, `APIGatewayToS3BucketMapping`
- **Parameter added**: `FrontendSPABucketName`
- New: `S3BucketPolicy` resource attached to `FrontendSPABucketName` (TLS 1.2 enforce, deny non-SSL)

> **Recommendation for v1 users:** skip v1 → v2 and go directly to v3 by filling `APIGatewayToS3BucketMapping` (and leaving `FrontendSPABucketName: ""`). v3 multi-bucket usage keeps the v1 routing pattern (no Lambda code rewrite) AND adds VPC attach + X-Ray IAM fix. The v1 → v2 → v3 path forces a Lambda code rewrite at the v2 step that v3 lets you avoid.

### v2 → v3 Migration

- All v2 parameters preserved unchanged
- **Add 3 new mandatory parameters** to the parameter file:
  - `VpcId` (e.g. `vpc-09528f37a12368b13`)
  - `SubnetIds` (comma-separated, min 2 private subnets in different AZs)
  - `VpcCidr1` (primary VPC CIDR for SG egress to Logs/X-Ray Interface Endpoints)
- The Lambda SG name is auto-generated by the template as `${AppShortName}-${EnvName}-s3ReverseProxy-sg` (matches v1's pattern — no parameter to fill)
- **Optional**: add `VpcCidr2-5` if multi-CIDR / shared-services / peered VPC
- **Optional**: add `S3PrefixListId` if using S3 Gateway endpoint (recommended — free, no data transfer cost)
- Verify Interface VPC Endpoints exist:
  - `com.amazonaws.{region}.logs` — for CloudWatch Logs writes
  - `com.amazonaws.{region}.xray` — for X-Ray traces
  - Both must be reachable from `SubnetIds`, with endpoint SG allowing inbound 443 from the new Lambda SG
- Create changeset and verify `LambdaS3ReverseProxy`, `LambdaExecutionRole` show **Modify** (not Replace), and `LambdaSecurityGroup` shows **Add**
- Execute changeset — no Lambda downtime, no recreation (~60–90s ENI provisioning during update window)
- Smoke test:
  - Hit the API → verify SPA assets load (S3 reverse proxy works)
  - Check CloudWatch Logs `/aws/lambda/{App}-{Env}-s3ReverseProxy` for entries (Logs egress works)
  - Check X-Ray service map for the function (X-Ray egress + IAM works)

### Direct v1 → v3 Migration

Two paths now available:

**Path A — keep multi-bucket routing (no Lambda code rewrite):**

- Carry `APIGatewayToS3BucketMapping` value forward from v1 unchanged
- Leave `FrontendSPABucketName: ""`
- Add the 3 new VPC parameters: `VpcId`, `SubnetIds`, `VpcCidr1` (SG name is auto-generated, no parameter)
- **No Lambda code rewrite needed** — v1 zip continues to work (still reads `API_TO_S3_BUCKET_MAP`)
- IAM scope: wildcard `${AppShortName}-*/*`; no managed bucket policy on the routed buckets (project team owns each bucket's policy).

**Path B — switch to single-bucket:**

- Provide `FrontendSPABucketName`
- Leave `APIGatewayToS3BucketMapping: ""`
- Lambda code MUST be rewritten to read `S3_BUCKET_NAME` env var
- Choose this if you only proxy to one bucket or want to consolidate from multi to single

## Version Recommendations

- **v1**: Legacy — upgrade recommended (no X-Ray, no VPC)
- **v2**: Stable but has latent X-Ray IAM bug — traces silently dropped despite TracingConfig.Mode: Active. **Not VPC-attached** (does not meet TISO compliance).
- **v3**: **Recommended** for new deployments — VPC-attached for TISO compliance, X-Ray tracing actually functional. Backward compatible at resource level (in-place modify only) with 4 new mandatory parameters.

For detailed changes, refer to the version-specific `README.md` files in each `vN/` directory.
